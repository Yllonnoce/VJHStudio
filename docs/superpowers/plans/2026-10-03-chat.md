# Chat Page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Chat page: saved conversations with RunWare text models, streamed replies, pictures from Assets and Gallery, cost per reply.

**Architecture:** A pure task builder and a `chat` service own the data and the RunWare call; a reply runs as a server task that emits events into a queue, and `POST /chat/send` relays them as an event stream read by `fetch`. Pages and message bubbles are server-rendered Jinja partials; `chat.js` only moves them into place.

**Tech Stack:** FastAPI, SQLAlchemy + Alembic (SQLite), Jinja2, htmx, plain JS, `runware-sdk` `client.stream()`, `markdown-it-py`.

**Spec:** `docs/superpowers/specs/2026-10-03-chat-design.md`

## Global Constraints

- Never print, log or render the API key. No paid calls in tests or browser checks (dummy key on a scratch instance, port 8091).
- `settings.maxTokens` is never sent. Pictures go in task-level `inputs.images`, every turn, only to `io:image-to-text` models.
- `POST` + `fetch` for the stream; no `EventSource`.
- ruff line length 100; tests first; no commits (the user commits).
- Every element inside an htmx form that issues its own request names its own `hx-target`.

## Review Focus

- Browser closes mid-reply: the partial text is saved as "stopped", nothing is left running.
- A reply that comes back empty (`finishReason: length`): shown as an error with Try again, not as a blank bubble.
- Model reply containing HTML/script or `javascript:` links: rendered inert.
- A picture deleted from Assets after it was attached: the conversation still opens and still sends.
- Retry after a failure: the user's message is sent once, not twice.

Each has a named test below.
